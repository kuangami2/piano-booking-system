# 房间预约系统：需求记录

状态：已定稿 v1，2026-09-06。

## 一、项目概述
琴房预约系统，面向少房间高自由度预约。用户端与管理端功能现阶段全部通过 Web 实现，后端 Spring Boot，数据库 MySQL。接口设计为前后端分离且无状态鉴权，为后续迁移微信小程序预留空间。

## 二、用户角色与注册
1. 普通用户：姓名、学号、邮箱注册，注册时自定义密码，提供修改途径。
2. 会员：在普通用户基础上提升优先级，可预约对内琴房。
3. 管理员：Web 后台，管理琴房、规则、用户与信用。
4. 密码找回：邮箱自助找回，实现从简，发送重置链接；管理员有重置权限。
5. 用户表预留微信 openid 字段，后续小程序迁移时可绑定。

## 三、场地管理
1. 琴房分对内与对外两类，会员可预约对内琴房，普通用户预约对外琴房。
2. 琴房数量暂定 5 间，后续可增加。
3. 每间琴房有详情说明，含乐器明细与注意事项，乐器独立成表一对多。
4. 每间琴房由管理端指定可约时间窗，如 6 点至 22 点。

## 四、预约规则（由管理端参数化配置）
1. 管理端参数配置（附默认值）：时间粒度（30min）、单次预约时长上限（4h，下限由最小单位保证）、提前预约天数上限（7d）、每周预约次数上限（3）、每周退约次数上限（2）。
2. 同一房间同一时段不允许重复预约，冲突即拒绝。
3. 随退随约，退约立即释放时段。
4. 无固定时段，可约时间窗内自由选择连续区间。
5. 时间推进自动化：预约按日期自然过期，状态自动进入已完成；可约窗口每日自动顺延；每周次数限制按自然周滚动；历史记录保留原表，量大时归档。

## 五、空出提醒
1. 用户想约的时段被占用时，可对该时段设置关注。
2. 该时段被退约释放后，通过站内提醒通知关注用户，先约先得，不设预留。
3. 通知实现做消息抽象，后续接小程序订阅消息时替换通道即可。

## 六、信用体系
1. 用户有随时间自然恢复的信用分，初始值与上限由管理端指定。
2. 仅人工减分：用户私下联系管理员反馈，管理员线下核实后减分，系统不做举报功能。
3. 信用分低于指定阈值，暂停预约服务。
4. 减分与恢复规则参数化，记录信用变更流水。

## 七、功能模块

用户端 Web：
1. 注册登录，姓名学号邮箱，自定义密码，找回与修改。
2. 首页轮播图片。
3. 系统公告。
4. 琴房列表与详情，含乐器明细，区分对内对外。
5. 琴房搜索。
6. 琴房预约，冲突提示与空出提醒设置。
7. 我的预约，支持取消。
8. 系统反馈。

管理端 Web：
1. 首页统计分析，琴房使用率与预约概况。
2. 用户管理，含会员设置与密码重置。
3. 琴房管理，含对内对外、乐器明细与注意事项。
4. 预约管理，查看与处理。
5. 规则参数配置，时长上下限、次数、提前天数、时间窗、最小单位。
6. 信用管理，人工减分与恢复。
7. 轮播与公告管理。
8. 反馈查看。

## 八、查询展示
1. 我的预约，按状态。
2. 琴房空闲查询，按日期与房间。
3. 按日期查看预约情况，管理端。

## 九、验收演示重点，按序演示
1. 注册登录、会员与改密找回。
2. 琴房浏览与搜索，对内对外区分。
3. 预约成功与冲突拒绝。
4. 退约后空出提醒生效。
5. 减分与暂停服务。
6. 管理端规则参数修改即时生效。

## 十、部署方式
本地部署为主，用户端与管理端 Web 本机可跑；后端接口无状态化，为小程序迁移留空间。

## 十一、迁移预留要点
1. 接口统一 REST 加 JWT，不依赖 Web 会话。
2. 用户表含微信 openid 字段，登录抽象可插微信授权。
3. 通知抽象消息通道，可替换为订阅消息。
4. 前端页面与接口分离，小程序端复用同一接口。

## 十二、v1.1 增强：异步消息、活跃度与取消风控

以下内容为 v1 之后的增强范围。阶段 A 缓存、索引与限流，阶段 B 活跃度排行榜与临近取消风控均已实现并通过验收，接口清单 v0.6；阶段 C 异步消息在验收后评估；全部增强以配置开关控制，依赖不可用时 v1 主链路可运行。

1. **RabbitMQ 异步消息**：退约后的空出提醒、活跃度事件、临近取消风控事件进入消息队列；预约创建、冲突检测、退约状态更新仍在数据库事务内同步完成，避免用户看到“预约成功”但实际未落库。消息发布采用事务 outbox 或提交后可靠投递、publisher confirm、持久化队列、手动 ack、有限重试与死信队列。
2. **用户活跃度排行榜**：记录登录、预约、退约、关注、消息已读、反馈等行为事件，按可配置权重累计分值。Redis ZSET 按周期保存（建议周榜和月榜），使用 `ZINCRBY` 更新分数、`ZREVRANGE ... WITHSCORES` 查询排名；排行榜允许最终一致，页面展示更新时间。
3. **临近时间取消黑名单**：将“预约开始前可配置窗口内的取消”记为一次临近取消；达到可配置次数后，将用户加入 Redis Set 黑名单并设置临时失效时间。Redis Set 只保存当前黑名单成员，用户到期时间放在独立 TTL 键（或由定时清理），避免误把永久封禁当作临时风控。命中黑名单时创建预约返回明确原因、解除时间与申诉提示；普通退约次数限制仍按原规则执行。
4. **幂等与可恢复**：每条领域事件携带唯一 `eventId`，消费者以 Redis `SET NX EX`（必要时配合数据库唯一索引）去重，处理成功后才 ack；重复投递不得重复累加排行榜分数、重复计数或重复发提醒。用户端提交按钮需防抖；若评审启用跨请求重试，再为预约/退约增加 `X-Idempotency-Key`。Redis/RabbitMQ 不可用时，核心预约写入仍可用，增强功能进入重试/补偿流程。
5. **用户体验**：用户端增加活跃度排行榜入口/组件、当前排名与分数展示；预约页在黑名单命中时展示剩余时间和规则说明；消息中心继续使用现有站内消息接口，不要求前端感知 RabbitMQ。

## 十三、后续版本需求

### （1）注册唯一性，防一人多号
1. 登录名、学号、邮箱三者均唯一，同一学号不得重复注册。
2. 学号与邮箱在数据库层补唯一索引兜底，应用层保留重复校验与字段级提示。
3. 验收：同一学号二次注册被拒且提示明确；并发注册同一学号仅一条成功。
4. 实现 2026-09-12：sys_user 补 uk_user_student_no 与 uk_user_email 唯一索引，应用层查重给出字段级提示，并发注册由唯一索引兜底并转成字段级提示，迁移脚本 migration_v1_2.sql。

### （2）注册与登录信息格式限制
1. 登录名：4 至 20 位，字母开头，可含字母数字下划线，或使用 10 位学号。
2. 密码：8 至 20 位，至少含字母与数字，不含空格，注册与改密一致。
3. 姓名：2 至 20 位汉字或字母，不含数字与符号。
4. 学号：10 位数字，与本校学号格式一致。
5. 邮箱：标准格式校验，是否限定校园邮箱域待定。
6. 前端即时提示与后端强校验双重执行，以后端为准，错误信息具体到字段。
7. 验收：非法格式在前后端均被拒并给出字段级提示，合法格式正常通过。
8. 实现 2026-09-12：引入参数校验依赖，注册与改密走独立请求对象校验，登录保持宽松以便历史账号继续登录，校验失败返回 400 与 data.field，用户端表单同步同口径规则并把后端错误落到对应输入框。

### （3）改密与找回统一
1. 已登录用户修改密码时提供忘记原密码入口，转入邮箱重置流程。
2. 重置流程：邮箱接收带时效令牌的重置链接，令牌一次性且过期失效。
3. 管理员重置权限保留，作为邮件通道不可用时的兜底。
4. 依赖邮件通道接入，见第二节密码找回。
5. 验收：忘记原密码可从改密页发起重置，凭链接重置后可用新密码登录。
6. 实现 2026-09-12：新增 password_reset 令牌表，申请找回生成 30 分钟一次性令牌并作废旧令牌，重置校验令牌后改密并作废该用户全部令牌，旧登录 token 随即失效；邮件通道未接入时按 app.mail.enabled 返回令牌便于联调，管理员重置保留兜底。

### （4）缓存一致性与高并发保护
1. 缓存一致性：热点读走缓存，写操作后主动失效，管理端改动后用户端在秒级内可见；前缀失效改用 SCAN 避免 KEYS 阻塞 Redis；同一时段并发预约由行锁加唯一约束保证不重复。
2. 未登录接口限流：登录与注册按来源限制频率，防止高频尝试与暴力破解消耗 CPU。
3. 缓存击穿保护：热点键失效瞬间的并发回源合并为一次查询，避免瞬时打满数据库。
4. 前端节流：提交防重复之外，列表刷新与日期切换等高频交互补充节流。
5. 并发压测验收：并发方式验证 50 与 100 并发下接口错误率与响应时间。
6. 现状：阶段 A 已实现热点缓存与主动失效、登录后单用户限流、连接池与索引调优、Redis 不可用降级。
7. 实现 2026-09-12：前缀失效改 SCAN 游标；未登录接口按来源 IP 每分钟 20 次限流；缓存未命中共用键级单飞合并回源；新增 tools/bench_concurrency.py，实测 50 并发 P50 11.8ms、100 并发 P50 9.2ms 且零失败，并发预约同一时段仅 1 条成功；修复 MyBatis 标准输出日志造成的串行化瓶颈，吞吐由 27 QPS 提升到 1867 QPS。前端节流仍待用户端实现。

## 十四、2026-09-17 检测需求
### （1）管理端取消预约须通知预约人（2026-09-17 已实现）
管理端取消预约原先只通知关注者，预约人无感知；要求取消时给预约人发站内消息，含琴房、日期、时段与取消来源，并与退约提醒区分消息类型。
### （2）退约与取消的操作反馈（2026-09-17 已实现）
已实现为用户退约后收到 booking_cancelled 确认消息；同账号自约自关注再自退时提醒逻辑排除本人，需以确认消息补足反馈。
### （3）管理端初始界面为登录页
本地有 token 时打开管理端会被重定向到首页，需先登出才能切换账号；要求打开管理端从登录页开始，不长期保留登录态。
### （4）新公告弹窗提醒
用户端登录或进入首页时，若存在未读公告则弹窗提示，已读后不再重复弹出。
### （5）预约交互提示与列表排序（2026-09-17 已实现）
预约提交时被拦截的每种情况都要给出明确提示，不得静默返回；双端预约记录按最新创建靠前排序。实现：用户端 valid 校验与受限态改为弹窗提示，双端排序改按自增主键倒序。
### （6）用户周配额管理
管理端可为指定用户设置本周额外预约与退约次数，用于特殊情况放行；周次数为实时统计而非计数器，故采用额外配额而非清零。评审草案见 docs/接口评审_阶段D.md。
### （7）管理端临时关闭琴房时段并释放预约
管理端可对指定琴房的日期区间临时关闭，取消区间内全部进行中预约并通知相关用户，关闭期间禁止新预约；实现前先评审接口与数据模型。

### （8）轮播图裁剪上传与容器比例锁定
现状：用户端轮播容器高度写死 260px 而宽度随屏幕变化，比例不固定，同一张图在不同屏幕被裁掉不同部分；管理端上传只提示格式与大小，无尺寸与比例指引，管理员无法确定该出多大图。
要求：整合为头像式裁剪上传。管理端选择图片后弹出裁剪框，比例锁定 21:9，拖动选区后确认，前端按 1260×540 导出 JPEG 再上传；用户端容器同时锁定 aspect-ratio 21:9 并用 object-fit cover 兜底，历史非标准比例图同样不破坏布局。
备注：不改后端接口，无需接口评审；裁剪组件可复用于琴房图片与公告配图。轮播比例与输出尺寸可在实现时按观感微调。
