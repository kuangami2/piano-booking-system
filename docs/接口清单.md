# 房间预约系统：接口清单

状态：v0.8，2026-09-17。v0.2 为历史基线，v0.3 增补 mine 接口 roomName，v0.4 补阶段 A 限流语义，v0.5 冻结阶段 B 排行榜与临近取消风控接口，v0.6 为阶段 B 联调收口修正，v0.7 落地改密与找回统一接口并补未登录 IP 限流语义，v0.8 冻结阶段 C 的事件总线与退约提醒异步化并新增管理端事件概览接口。

## 一、约定
1. 基础路径 /api，请求与响应 JSON，UTF-8。
2. 统一响应 Result：{code,msg,data}。code 200 成功，400 参数或规则校验失败，401 未登录或 token 失效，403 无权限，404 资源不存在，409 业务冲突如时段被占、周次数超限。
3. 鉴权无状态 JWT：登录返回 token，请求头携带 token，公开接口为注册、登录、找回密码。
4. 分页参数 page 从 1 起，size 默认 10，data 返回 {list,total}。
5. 时间表达：预约、关注与空闲均用当日分钟整数 startMin、endMin，如 600 表示 10 点；粒度按最小单位 30 分钟对齐，由后端校验。
6. 日期用 YYYY-MM-DD，入参与出参一致，实体日期字段以 @JsonFormat 固定该格式，避免序列化为数组。
7. 限流：预约创建与关注按用户每分钟 10 次，排行榜与风控查询按用户每分钟 30 次，登录、注册、找回与重置按来源 IP 每分钟 20 次，超限统一返回业务码 429；缓存对客户端透明，不新增接口。

## 十六、契约评审结论，2026-09-07 组长收口
1. 鉴权头定为 token，与管理平台脚手架生态一致，公开接口仅注册、登录、找回。
2. 时间参数定为当日分钟整数，前端展示自行换算，粒度与时长由后端校验。
3. 琴房删除策略：无预约与乐器记录时物理删除，有关联记录返回 409，状态停用逻辑后续版本补。
4. 管理端接口统一 /api/admin 前缀并加 @RequireRole("admin")，实现时逐个补齐校验。
5. 契约 v0.2 冻结为开发基线，新增或变更先改本文档再实现。

## 十七、阶段 B 接口：排行榜与取消风控（v0.5 已冻结 2026-09-10）

本节为阶段 B 已冻结接口，2026-09-10 全员评审通过。结论：排行榜分页默认 1 与 20，同分按 userId 升序，隐私仅返回昵称脱敏；风控参数复用 /api/admin/rules 新增三项；命中风控时预约创建返回 409 并在 data 带解除时间与次数；排行榜最终一致、风控判断强一致；本期不做请求级幂等；排行榜与风控接口每分钟 30 次限流。阶段 C 只做 MQ 事件总线与提醒异步化。评审记录见 docs/接口评审_阶段B.md。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/rankings/activity | 活跃度排行榜；参数 `period=week\|month`、`page`、`size`；data 返回 `{list:[{rank,userId,name,score}],me:{rank,score},updatedAt}`，分数与排名允许最终一致 |
| GET | /api/risk/near-cancel | 当前用户临近取消风控状态；data 返回 `{active,until,reason,nearCancelCount}`；仅返回本人信息 |

预约创建命中黑名单时沿用 409 业务冲突码，并在 `msg` 或扩展 data 中返回解除时间；RabbitMQ 的 `eventId`、重试和幂等字段为内部消息契约，不暴露给用户端。

v0.6 联调收口修正，2026-09-12，前后端实测后确认：

1. 预约创建成功时 data 返回写入后的预约记录，含自增 id、状态与日期，未命中风控与冲突时恒非空。
2. 风控受限期间 nearCancelCount 回传触发阈值次数，不再回传重置后的 0，与解除时间口径一致。
3. 排行榜只统计普通用户与会员，管理员行为不计分也不上榜。
4. 日期出参统一为 YYYY-MM-DD 字符串，此前预订与关注记录曾序列化为数组，与本节第 6 条不符，已修正。

v0.7 功能迭代，2026-09-12：

1. 找回与重置落地：password_reset 表存一次性令牌，有效期 30 分钟；重复申请会作废旧令牌，重置成功后该用户全部令牌作废；管理员重置接口保留为邮件通道不可用时的兜底。
2. 未登录接口按来源 IP 限流每分钟 20 次，反向代理场景取 X-Forwarded-For 首个地址。
3. 注册唯一性与字段格式校验同轮落地，注册与改密走字段校验，登录保持宽松以便历史账号继续登录。

## 十八、阶段 C 接口与消息契约（v0.8 已冻结 2026-09-15）

本节为阶段 C 已冻结内容，2026-09-15 全员评审通过，评审记录见 docs/接口评审_阶段C.md。范围为退约提醒异步化与事件总线，其余事件只做发布预留；用户端接口与页面零改动，提醒仍通过 messages 接口读取。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/admin/events/summary | 事件与投递概览，管理员专用，每分钟 30 次限流；data 返回 `{mqEnabled,mode,brokerReachable,outbox:{pending,sent},dlq:{depth,redelivered},events:[{eventType,count}],lastEventAt}`；broker 不可达时 `brokerReachable` 为 false，outbox 与 dlq 字段返回 null 而不报错 |

字段语义：
1. `mode` 取 `async` 或 `degraded`，分别表示事件走 MQ 异步投递或当前处于同步降级。
2. `outbox.pending` 与 `outbox.sent` 为本地消息表按状态计数，用于对账。
3. `dlq.depth` 为死信队列当前深度，`dlq.redelivered` 为累计重投次数。

内部消息契约，不暴露给用户端：
1. 交换机 `room.events` 为 topic 类型，路由键 `booking.cancelled`，队列 `room.notify.vacancy` 绑定该键并持久化；配死信交换机 `room.events.dlx` 与死信队列 `room.events.dlq`。
2. 消息信封统一为 `{eventId,eventType,occurredAt,version,payload}`，`booking.cancelled` 的 payload 携带 bookingId、userId、roomId、roomName、bookDate、startMin、endMin 完整快照，消费者不回查数据库。
3. 业务事务内写 `event_outbox`，记录来源 `source` 取 `normal` 或 `degraded`；提交后投递，失败留 `pending` 由定时任务按 `outbox-retry-seconds` 退避重投，超过 `outbox-max-retry` 停止。
4. 消费者以 `processed_event` 表的 eventId 主键幂等去重，手动确认；业务异常不重回队列，进 DLQ 后按 `dlq-max-redelivery` 独立计数重投，与 outbox 的投递重试互不影响。
5. 降级路径：`app.enhance.mq-enabled` 关闭或 broker 不可达时，发布方按 `mq-publish-timeout-ms` 快速失败并同步执行提醒，同时写一条 `source=degraded` 的 outbox 记录供对账。

如需支持网络重试下的请求级幂等，v0.3 评审时为 `POST /api/bookings` 与 `DELETE /api/bookings/{id}` 增加可选请求头 `X-Idempotency-Key`；同一用户、同一业务键在有效期内返回相同结果。
