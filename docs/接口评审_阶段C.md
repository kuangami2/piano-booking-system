## 一、评审范围
1. 事件总线基础设施：事件类型、交换机与队列命名、路由键、消息信封结构、投递语义。
2. 退约提醒异步化：退约事件驱动站内空出提醒生成，替代当前在事务内同步写消息的做法。
3. 降级与不可用路径：MQ 未启动或 broker 不可达时，预约主链路与提醒功能必须照常可用。
4. 可靠性：本地消息表、幂等、重试退避与死信。
5. 是否新增管理端事件概览接口。
6. 数据模型变更：event_outbox 与 processed_event 两张表与迁移脚本。
7. 本次不纳入：请求级幂等 X-Idempotency-Key、排行榜与计分的异步化改造、邮件与短信通道接入。

## 二、待确认要点与建议方案
1. 范围边界：建议本期只把退约触发的空出提醒异步化，预约创建、过期完成、信用变更等事件只做发布预留，不改动现有同步实现。备选是全部事件异步化，范围与回归风险都显著变大。
2. 投递模型：建议 topic 交换机 `room.events`，路由键 `booking.cancelled`，队列 `room.notify.vacancy` 绑定该键；另建死信交换机 `room.events.dlx` 与死信队列 `room.events.dlq`。备选用 direct 交换机，实现更简单但后续扩展要改绑定。
3. 消息信封：建议统一为 `eventId`、`eventType`、`occurredAt`、`version`、`payload`；`booking.cancelled` 的 payload 含 bookingId、userId、roomId、roomName、bookDate、startMin、endMin。备选是只传 bookingId 由消费者回查，一致性强但多一次数据库查询，且琴房已删时无法还原名称。
4. 可靠性：建议引入本地消息表 `event_outbox`，业务事务内与预约状态变更同事务写入，事务提交后投递 MQ；投递成功置 sent，失败留 pending 由定时任务按退避间隔重投。备选是提交后直接投递不落表，实现简单，但 MQ 停机期间的事件会永久丢失，与提醒的可靠性要求不符。
5. 不可用降级：建议总开关 `app.enhance.mq-enabled`，默认 true；broker 不可达时发布方按 `mq-publish-timeout-ms` 默认 500 毫秒快速失败，随即同步执行提醒，保证用户立刻收到；outbox 留 pending 记录，MQ 恢复后重投并由幂等拦截重复。备选是只记 outbox 不降级，提醒延迟到 MQ 恢复，用户侧会出现提醒迟到。评审补充并采纳：降级路径同时写一条 source 为 degraded 的 outbox 记录，供概览页对账。
6. 幂等：建议新增 `processed_event` 表，以 eventId 为主键，消费者插入成功才继续处理，重复投递直接确认并丢弃。备选是复用 message 表加唯一键，改动现有表结构风险高；或用 Redis SETNX，本机未装 Redis，不可取。
7. 消费语义：建议手动确认，处理成功确认；业务异常不重回队列，直接进死信队列，再由定时任务按次数重投。消息持久化，队列持久化。备选是自动确认，实现简单但异常即丢消息。评审补充并采纳：DLQ 重投次数用独立配置 dlq-max-redelivery 默认 5，与 outbox-max-retry 各自计数、互不影响。
8. 管理端事件概览接口：建议新增 `GET /api/admin/events/summary`，返回各事件类型计数、outbox 的 pending 与 sent 数量、死信队列深度与最近事件时间，加管理员角色校验并按每分钟 30 次限流；便于演示异步链路与答辩讲解。备选是不加接口，只在日志与 RabbitMQ 管理台查看。评审补充并采纳：响应含 mqEnabled、mode 与 brokerReachable，broker 不可达时 outbox 与 dlq 字段返回 null 而不报错，页面转为提示降级运行。
9. 配置项：建议 `spring.rabbitmq` 指向 127.0.0.1 的 5672，账号 guest 密码 guest；新增 `app.enhance.mq-enabled`、`mq-publish-timeout-ms` 默认 500、`outbox-retry-seconds` 默认 30、`outbox-max-retry` 默认 10；发布方不做启动即失败，保证 MQ 未启动时应用仍能启动。备选是把超时与重试写死在代码里。
10. 接口冻结：建议本草案通过后接口清单升 v0.7 并标注阶段 C 冻结，v0.6 与 v0.7 继续作为阶段 A、B 与功能迭代的基线；用户端接口无新增无变更。
11. 开关默认值：建议 `mq-enabled` 在 application.yaml 中默认 true，本机与演示环境已装 RabbitMQ；组员本地若未装可置 false 走同步降级，不影响主链路。
12. 演示口径：建议验收时把「停掉 RabbitMQ 服务后提醒仍能送达」作为降级能力的展示点，与阶段 A 的 Redis 降级形成呼应。

## 四、影响面
1. 用户端：接口与页面均不变，站内提醒仍走 messages 接口，仅投递路径由同步改为异步，用户无感知。
2. 管理端：若采纳第 8 项，新增事件概览接口与页面各一，复用现有管理端框架。
3. 数据库：新增 event_outbox 与 processed_event 两张表，迁移脚本 migration_stage_c.sql，建库脚本同步更新，重建库时无需单独再跑。
4. 依赖：后端新增 spring-boot-starter-amqp；本机 RabbitMQ 4.3.6 与 Erlang OTP 27.2 已就绪，服务按需手动启动，管理台 http://localhost:15672。
5. 风险：MQ 不可用时必须有降级路径，否则违反依赖不可用时 v1 主链路必须可运行的既有纪律；消费者必须幂等，否则重投会产生重复提醒。
