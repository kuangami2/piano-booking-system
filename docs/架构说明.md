# 房间预约系统：架构与设计

## 一、技术栈决策
1. 后端：Spring Boot 3.5 加 MyBatis-Plus 3.5.9 加 MySQL，以管理平台脚手架为骨架，jakarta 体系。该脚手架提供 Spring Boot 分层骨架、Vue3 前端模板、双角色 JWT 鉴权与统一返回，原名 3+3 脚手架融合管理平台。
2. 用户端与管理端均为 Web 独立工程，Vue3 加 Vite 加 Element Plus，骨架 2026-09-07 定稿于 frontend/user-web 与 frontend/admin-web。
3. 小程序迁移预留：接口统一 REST 加 JWT 无状态，用户表含微信 openid，登录与通知做抽象，前端与接口分离。
4. 2+2 脚手架与参考项目 RoomReservationSystem 为 Boot 2.5 旧栈，仅作业务参考不采用。
5. 并发方案：预约事务内先读规则快照再查冲突再写，规则缓存修改时刷新；写路径先对房间行 SELECT ... FOR UPDATE 串行化同房并发，再查区间重叠后插入，uk_book_slot 唯一键兜底同房同日同起点重复。
6. v1.1 候选中间件：RabbitMQ 用于领域事件异步解耦，Redis 用于排行榜与轻量风控状态。两者不可用时不得阻断预约核心写路径；正式引入前补充本地部署配置、监控和验收脚本。

## 二、分层设计
1. controller 路由层，参数校验，调 service。
2. service 业务层，预约规则校验与冲突检测，信用与提醒逻辑。
3. mapper 数据层，MyBatis-Plus 加 XML。
4. entity 加 dto 加 common，统一 Result，JWT 拦截，全局异常。
5. 用户端与管理端各自前端工程，共用后端接口，按角色接口分组。

## 三、数据模型
1. sys_user 用户表，姓名学号邮箱，role 区分 user 与 admin，is_member 会员标记，credit 信用分，openid 预留微信。
2. room 琴房表，room_type 区分 inner 对内与 outer 对外，open_start 与 open_end 为可约窗分钟，360 表示 6 点。
3. instrument 乐器表，room 一对多。
4. rule_config 规则参数表，键值存储，管理端可调，修改后刷新缓存即时生效。
5. booking 预约表，book_date 加 start_min 与 end_min 存区间，状态 booked、cancelled、finished，uk_book_slot 并发兜底。
6. watch 空出提醒关注表，用户对房间日期区间关注，uk_watch_slot 防重复关注。
7. credit_log 信用流水表，记录人工减分与恢复，含经办管理员。
8. feedback 反馈表。
9. message 站内消息表，通知通道抽象，msg_type 区分类型，is_read 已读标记。
10. notice 公告表。
11. banner 轮播图表。
12. v1.1 候选 `outbox_event` 表：保存事件 ID、类型、负载、状态、重试次数和下次投递时间，与业务更新同事务写入；是否落表及字段以评审后的可靠投递方案为准，v0.2 基线仍为前述 11 表。

## 五、v1.1 异步与 Redis 设计（候选）

### 1. 事件流与边界

预约创建、退约状态变更、冲突检测和信用校验继续由 Booking Service 在 MySQL 事务内同步完成。事务提交后发布 `BookingCancelled`、`VacancyNotified`、`UserActivityRecorded`、`NearCancelDetected` 等事件；空出提醒、活跃度累加和取消次数统计由 RabbitMQ 消费者异步处理。推荐使用事务 outbox（outbox 记录与业务更新同库同事务）或可靠的提交后发布，配合 publisher confirm、持久化 exchange/queue、手动 ack、指数退避重试和死信队列。

### 2. 活跃度排行榜（Redis ZSET）

- 事件携带 `eventId`、`userId`、`eventType`、`occurredAt`；登录、预约、退约、关注、消息已读、反馈等行为按 `rule_config` 中的权重计分。
- 建议规则键：`activity.weight.login`、`activity.weight.booking`、`activity.weight.cancel`、`activity.weight.watch`、`activity.weight.messageRead`、`activity.weight.feedback`；临近取消窗口、触发次数和黑名单时长使用 `risk.nearCancelWindowMin`、`risk.nearCancelThreshold`、`risk.blacklistDurationMin`，具体默认值由管理端评审确定。
- 约定键名：`rr:rank:activity:week`、`rr:rank:activity:month`，member 为用户 ID，score 为累计分值；消费者使用 `ZINCRBY`，查询使用 `ZREVRANGE ... WITHSCORES` 与 `ZREVRANK`。按周期设置过期或在周期切换时新建 key，避免全量重算。
- 排行榜为最终一致数据，接口返回 `updatedAt`；分数相同按用户 ID 做稳定的二级排序。对外仅返回必要的昵称/脱敏学号，避免泄露隐私。

### 3. 临近取消黑名单（Redis Set）

- 退约事件根据“距预约开始的分钟数”判断是否临近取消；窗口、触发次数、黑名单时长均由规则参数配置。
- 约定 `rr:risk:near-cancel:blacklist` 为 Set，成员为当前黑名单用户 ID；`SISMEMBER` 在创建预约前快速拦截。由于 Set 不支持成员级 TTL，每个用户另存 `rr:risk:near-cancel:expire:{userId}` TTL 键，并由定时任务清理过期成员；必要时用 Lua 将检查、计数和加入黑名单合并为原子操作。
- 临近取消计数采用按用户/周期的计数键或事件明细，不能只依赖 Set（Set 只能表达是否在黑名单）。命中时返回 `active/until/reason`，到期自动解除；该风控不替代原有每周退约次数规则。

### 4. 幂等、故障与补偿

- 生产者为每个领域事件生成全局唯一 `eventId`，outbox 对其建唯一约束；消费者先以 Redis `SET rr:idem:{eventId} 1 NX EX <ttl>`（Redis 不可用时降级为数据库唯一表）去重，业务处理成功后再 ack。
- 用户端对预约/退约按钮做防抖；若接口需要在网络重试下保持同一请求只生效一次，候选 v0.3 增加 `X-Idempotency-Key`，后端以请求键绑定用户和业务结果并设置合理过期时间。
- 重投、消费者重启或网络抖动不得重复累加 ZSET 分数、重复计入临近取消或重复发送站内提醒；失败消息进入重试队列，超过次数进入 DLQ 并告警，支持人工补偿。
- 监控至少覆盖队列积压、消费失败/DLQ、Redis 命中率与黑名单误拦截；增强链路故障时保留同步预约能力。
