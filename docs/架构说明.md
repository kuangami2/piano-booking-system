# 房间预约系统：架构与设计

## 一、技术栈决策
1. 后端：Spring Boot 3.5 加 MyBatis-Plus 3.5.9 加 MySQL，以管理平台脚手架为骨架，jakarta 体系。该脚手架提供 Spring Boot 分层骨架、Vue3 前端模板、双角色 JWT 鉴权与统一返回，原名 3+3 脚手架融合管理平台。
2. 用户端与管理端均为 Web 独立工程，Vue3 加 Vite 加 Element Plus，骨架 2026-09-07 定稿于 frontend/user-web 与 frontend/admin-web。
3. 小程序迁移预留：接口统一 REST 加 JWT 无状态，用户表含微信 openid，登录与通知做抽象，前端与接口分离。
4. 2+2 脚手架与参考项目 RoomReservationSystem 为 Boot 2.5 旧栈，仅作业务参考不采用。
5. 并发方案：预约事务内先读规则快照再查冲突再写，规则缓存修改时刷新；写路径先对房间行 SELECT ... FOR UPDATE 串行化同房并发，再查区间重叠后插入，生成列 active_slot 上的唯一索引 uk_book_active_slot 兜底进行中预约的重复写入。
6. 增强中间件现状：Redis 已在阶段 A 缓存与限流、阶段 B 排行榜与风控中使用，不可用时按设计回退进程内实现，不阻断预约核心写路径；RabbitMQ 用于阶段 C 的领域事件异步解耦，尚未引入。

## 二、分层设计
1. controller 路由层，参数校验，调 service。
2. service 业务层，预约规则校验与冲突检测，信用与提醒逻辑。
3. mapper 数据层，MyBatis-Plus 加 XML。
4. entity 加 dto 加 common，统一 Result，JWT 拦截，全局异常。
5. 用户端与管理端各自前端工程，共用后端接口，按角色接口分组。

## 三、数据模型
1. sys_user 用户表，姓名学号邮箱，role 区分 user 与 admin，is_member 会员标记，credit 信用分，openid 预留微信。
2. room 琴房表，room_type 区分 inner 对内与 outer 对外，open_start 与 open_end 为可约窗分钟，360 表示 6 点。
3. instrument 乐器表，room 一对多。
4. rule_config 规则参数表，键值存储，管理端可调，修改后刷新缓存即时生效。
5. booking 预约表，book_date 加 start_min 与 end_min 存区间，状态 booked、cancelled、finished；生成列 active_slot 仅在 status 为 booked 时取值，唯一索引 uk_book_active_slot 只约束进行中预约，退约与完成不阻塞后续预约。
6. watch 空出提醒关注表，用户对房间日期区间关注，uk_watch_slot 防重复关注。
7. credit_log 信用流水表，记录人工减分与恢复，含经办管理员。
8. feedback 反馈表。
9. message 站内消息表，通知通道抽象，msg_type 区分类型，is_read 已读标记。
10. notice 公告表。
11. banner 轮播图表。
12. 阶段 C 候选 `outbox_event` 表：保存事件 ID、类型、负载、状态、重试次数和下次投递时间，与业务更新同事务写入；是否落表及字段以评审后的可靠投递方案为准，当前基线仍为前述 11 表。

## 五、v1.1 增强设计

### （1）阶段 A：缓存、限流与数据库调优
1. 缓存：琴房列表、琴房详情、规则参数与空闲查询结果走 CacheService，Redis 优先，不可用时回退进程内并暂停重试 30 秒；写操作按前缀主动失效，管理端改动秒级可见。
2. 限流：RateLimitService 固定窗口计数，预约创建与关注按用户每分钟 10 次，排行榜与风控查询每分钟 30 次，超限返回业务码 429。
3. 数据库：HikariCP 连接池调优，booking 与 watch 补查询索引，压测数据见 性能与可靠性设计.md。
4. 开关：app.enhance.cache-enabled 与 rate-limit-enabled，关闭即回退原路径。

### （2）阶段 B：活跃度排行榜与临近取消风控
1. 计分：登录 1、预约 5、退约负 3、关注 2、消息已读 1、反馈 2，键为 activity.weight.*；Redis ZSET 周键与月键按周期滚动，只统计普通用户与会员。
2. 风控：退约时距预约开始不足 risk.nearCancelWindowMin 分钟计一次临近取消，达 risk.nearCancelThreshold 次进入临时黑名单 risk.blacklistDurationMin 分钟；创建预约前强一致拦截，命中返回 409 并带解除时间、原因与次数。
3. 降级：Redis 不可用时计分与计数回退进程内实现，单实例演示可用，重启后状态清零。
4. 接口、降级与验收细节见 排行榜与风控设计.md，契约见 接口清单.md 第十七节。

### （3）阶段 C 候选：异步消息与可靠投递
1. 退约提醒、活跃度事件与风控事件改由 RabbitMQ 异步处理，预约创建、冲突检测、退约状态更新仍在数据库事务内同步完成。
2. 采用事务 outbox 或提交后可靠投递，配合 publisher confirm、持久化 exchange/queue、手动 ack、指数退避重试与死信队列；消费者以唯一 eventId 幂等去重。
3. 用户端对预约与退约按钮做防抖；若启用跨请求重试，为预约与退约增加可选 X-Idempotency-Key。
4. 监控覆盖队列积压、消费失败与死信、Redis 命中率与黑名单误拦截；增强链路故障时保留同步预约能力。
