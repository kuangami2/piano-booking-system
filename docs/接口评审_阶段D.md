# 阶段 D 接口评审草案

状态：草案，待全员评审。本草案覆盖可约区间变更管理与用户周配额管理两项需求，通过并升接口清单 v0.9 冻结后再实现。

## 一、评审范围
1. 琴房可约时间窗变更后的预约同步：修改每日时间窗导致既有预约越界时的处理。
2. 临时关闭琴房指定日期时段，以及关闭区间内预约的处理。
3. 受影响预约的用户通知与关注者提醒。
4. 变更预览：管理端保存前先看将影响多少条预约，确认后再执行。
5. 用户周配额管理：管理端为指定用户设置本周额外预约与退约次数，用于特殊情况放行。
6. 数据模型新增两张表与相应接口。

## 二、待确认要点与建议方案
1. 范围合并：建议把修改时间窗与临时关闭统一为可约区间变更，共用受影响预约计算与通知链路。备选是只做临时关闭，时间窗变更维持现状。
2. 越界预约处理策略：建议自动取消并通知，管理端返回受影响清单；备选是只标记待处理交由管理员逐条决定，实现更复杂且容易遗漏。
3. 预览与确认：建议保存时间窗前调用预览接口先返回受影响预约数量与清单，管理端二次确认后再提交；备选是直接保存并静默处理。
4. 临时关闭的存储：建议新增 room_closure 表，字段为 room_id、close_date、start_min、end_min、reason、created_by、created_at、status；备选是复用 room.status，粒度不足。
5. 关闭期间禁止新预约：建议预约创建时校验是否落在关闭区间，命中返回 409 并说明原因。
6. 关闭撤销：建议关闭记录支持撤销，撤销只改自身状态，不回滚已取消的预约，保留历史。
7. 通知类型：建议新增消息类型 room_unavailable，内容含琴房、日期、时段与原因，区分为时间窗调整或临时关闭；预约人被取消时同时触发关注者空出提醒。
8. 配额机制：建议新增 user_quota 表，字段为 user_id、week_tag、extra_book、extra_cancel、reason、created_by、created_at；校验时使用规则上限加额外配额。备选是给用户加豁免周标识，无法只放宽几次。
9. 周口径：沿用 ISO 周标识，与排行榜周榜一致，形如 2026-W38。
10. 配额查询：建议管理端用户列表或详情返回本周配额与已用次数，便于核对。
11. 接口冻结：建议本草案通过后接口清单升 v0.9 并新增阶段 D 一节，v0.8 继续作为阶段 C 基线。
12. 分期建议：D1 临时关闭与越界处理加通知，D2 时间窗变更预览，D3 用户配额管理；三项均有独立开关可降级。

## 三、接口草案
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/admin/rooms/{id}/closures | 临时关闭指定日期时段，body 含 date、startMin、endMin、reason；data 返回受影响并取消的预约数 |
| GET | /api/admin/rooms/{id}/closures | 关闭记录列表，可按日期过滤 |
| DELETE | /api/admin/closures/{id} | 撤销关闭，仅改关闭记录状态 |
| POST | /api/admin/rooms/{id}/window-preview | 时间窗调整预览，body 含 openStart、openEnd；data 返回受影响预约清单，不写库 |
| PUT | /api/admin/rooms/{id} | 既有接口，调整时间窗时若带 confirmImpact 为真则按策略取消越界预约并通知 |
| GET | /api/admin/users/{id}/quota | 查询指定用户本周配额与已用次数 |
| PUT | /api/admin/users/{id}/quota | 设置本周额外预约与退约次数，body 含 extraBook、extraCancel、reason |

受影响预约判定：进行中预约的日期与时段，与新的每日时间窗不兼容，或与任一有效关闭区间重叠。

## 四、影响面
1. 数据库：新增 room_closure 与 user_quota 两张表，迁移脚本 migration_stage_d.sql，建库脚本同步。
2. 接口：新增六到七个管理端接口，接口清单升 v0.9；用户端无新增接口，但预约页需展示关闭提示。
3. 前端：管理端琴房页新增临时关闭入口与影响预览，用户管理页新增配额设置；用户端琴房详情展示关闭状态。
4. 依赖：不引入新中间件，通知复用现有消息表与事件总线。
5. 风险：批量取消预约属高影响操作，必须有预览确认与受影响清单留痕。
